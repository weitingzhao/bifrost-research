# Research 蓝图

> **这是目标，不是功能清单，也不是现状。** 它回答"Research 理想中应该是什么"。
> 代码离它多远、差在哪、先修什么，在另一份文档《Research 校准》里，那份会随现状不断变，这份不会。
> 章节编号与契约编号（`C-F1` 这种）是**稳定锚点**：内容可以改，编号不改，校准按编号引用。
> 同一份文件：仓库 `bifrost-research/src/bifrost_research/docs/RESEARCH_BLUEPRINT.md`，
> API `GET /research/docs/blueprint`，UI `/docs/research-blueprint`。三处一个源。

## 0. 两份文档怎么分工

**校准流程**：拿 §4 的每条契约问代码"今天满足吗"，答案和证据写进校准文档；不满足的写最小改动；排序另议。蓝图本身只在"我们对 Research 的理解变了"时才改，每次改动记进 §7。

## 1. 一句话定位

Research 是 Bifrost 的**决策载荷**：它产出判断，不产出订单。交易执行冻结（spine D10）；它只写 `dw_stock.*`、`features.*`、`research.*`，只读 `raw_market.*`，不碰 Trade DB（D13）。

它对人的价值，按重要性排序：

1. 说出人不知道的东西。
2. 说出的东西事后被证明是对的。
3. 说清楚为什么，以及什么情况下它错了。

## 2. 四层模型

三个面向人的姿态，加一个它们共用的记忆。依赖方向从下往上。

```
                ┌──────────────────────────────────────┐
                │  操作面 · Copilot                     │  人和 LLM 的工作台：
                │  直接调基础层、实绩层做任何研究；        │  问、算、验、写
                │  智囊的报告是它的输入之一               │
                └───────────┬──────────────────────────┘
                            │  报告回流，可追问
            ┌───────────────┴──────────────────────────┐
            │  智囊 · Analyst（今名 Autopilot）          │  判断层：
            │  按 objective 分析、判官、评级、解释         │  Bifrost Rating 是它的产物
            └───────────────┬──────────────────────────┘
                            │  读数经 lenses，战绩经实绩层
  ┌─────────────────────────┴────────────────────────────┐
  │  基础层 · Foundation                                  │  能力层：
  │  engines + lenses + feature store                    │  每个分析面一份实现
  │  （Workbench 页面是它最薄的一层皮）                    │
  └─────────────────────────┬────────────────────────────┘
                            │
  ┌─────────────────────────┴────────────────────────────┐
  │  实绩层 · Record                                      │  记忆层：
  │  提过什么 · 批过什么 · 后来到底怎么样了                │  每个"后来怎么样"一个定义
  └──────────────────────────────────────────────────────┘
```

形状是**扇形加一条回边**：基础层分叉出智囊和 Copilot，两者各自都能完整地使用它；智囊的报告回流到 Copilot 被追问。实绩层被三者读，被智囊和 Copilot 写。这个形状回答"新东西该放哪"：**可复用的分析原语**落基础层；**判断、评级、解释**落智囊；**人要读、要问、要自己动手算的**落 Copilot；凡是"后来怎么样了"落实绩层。

### 2.1 基础层 · Foundation

**是什么**：全部分析**原语**的唯一实现。`engines/`（波动、动量、GEX、资金流、预测、回测、信号衰减、候选结清……）、`lenses/`（registry、exhibits、track_record）、`features.*` 特征表、`dw_stock.*` dbt 宽表。

**入口**：`lenses/exhibits.build_exhibit` 是读基础层的正门。页面判定条、Copilot 的 `research.exhibit.get`、daily brief 已经走这一个入口，蓝图把它升格为规则。

**拥有**：每个 lens 的定义、band、读数、说明文案；每个引擎的计算；特征表的写入。

**禁止**：不知道 objective 是什么；不知道谁在问；不写 `research.*` 里的提案与审批。

**Workbench 的位置**：Workbench 的页面是基础层最薄的一层皮，直接把面摆给人看。它是一个界面，和 Copilot、智囊平级，**不是**基础本身。说"接上 Workbench 的能力"时，指的是 import `lenses/`，不是调 Workbench 的 API。

**理想状态**：任何一个分析原语，全系统只有一份实现，三个姿态读的是同一份；每个 lens 对它覆盖的每个标的都真的会触发。

### 2.2 实绩层 · Record

**是什么**：系统对自己战绩的记忆。它不是分析能力，也不是交互，是让另外三层**可改进**而不只是可运行的那一层。

**拥有**：
- 提过什么，每条的当时样子（候选池与 `lens_snapshot`）
- 提出之后到底怎么样了（候选结清，按 horizon、对基准）
- 每个 lens 触发后的命中（信号衰减表）
- 回测跑过什么、结果如何
- Owner 说过"不"的名字和当时的读数（拒绝记忆）
- 谁、何时、花了多少、做了什么（行动账）

**为什么单独成层**：一个没有名字的层会被建很多遍，而且每一遍口径都略有不同。"后来怎么样了"是四个不同的问题（lens 命中率、候选来源命中率、回测胜率、预测命中率），每个问题该有**一个**定义、**一个**实现、**一张**表；谁要用，来这里拿。

**理想状态**：每一个"后来怎么样了"的问题有且只有一个定义；提出的每个候选都会被结清；每个触发都会被回填命中；智囊的评级和 Copilot 的回答引用的是同一份战绩。

### 2.3 智囊 · Analyst（今名 Autopilot）

**是什么**：**判断层**。按预设 objective 自动完成一次完整的研究：决定看什么，读基础层拿读数，读实绩层拿战绩，跑回测验证，请判官（多个模型）各自表态，然后**给出评级**：这个名字值不值得看、有多确定、现在是不是时候、位置在哪、用什么工具、为什么、什么情况下这个判断是错的。产出是一份**带证据、带判官意见、带评级、带失效条件的报告**，等人批。它不执行，不下单，不扩容（D10）。

**它必须做分析。** 这一点要说清楚，因为上一版把它写成了照本宣科的编排器，那不是需要的东西。智囊的本职就是：把基础层的读数、实绩层的战绩、回测的验证、判官的立场**合成一个判断**。今天的 Smart Decision Run 就是这个层的参考实现，Bifrost Rating 就是它的产物：

| 评级维度 | 回答什么 | 来源 |
|---|---|---|
| conviction | 有多确定 | 结清战绩 + 判官立场，战绩压过判官 |
| action | 该怎么做（watch / hold_no_add / avoid …） | grade + conviction + 判官是否阻断 |
| timing | 现在是不是时候 | 价格相对 pivot / 均线 |
| levels | 止损、目标在哪 | R 倍数 |
| outlook | 相对上次好了还是坏了 | 分数对 prior |
| instrument | 用股票还是期权 | stage + IV rank |
| why / wrong_if | 为什么，以及什么情况下错了 | 以上全部 |

**它的纪律只有一条**：不重新发明原语。读数来自 lenses，战绩来自实绩层的那一个定义，回测来自回测引擎。智囊拿这些东西**做判断**，不自己再写一份 SEPA 筛选、不自己再写一份命中率 SQL。这条纪律不是限制它的能力，而是保证它算出来的东西和 Copilot、和页面看到的是同一个数。

**它有一个谱**，同一层，两端都要：
- **基础一端**：按 objective 跑一遍，把读数、战绩、判官意见原样摆出来，评级从简。适合新 objective 冷启动、或者人只想要一份快照。
- **高级一端**：完整的 Smart Decision——多层筛选、逐标的证据、回测验证、多判官、评级、解释、绳子。这是主要形态。

**产出的度量**（对应 §1 的三条）：
- 新信息率：报告里有多少名字是人最近没见过、也没拒绝过的。
- 事后正确率：报告提出的名字，结清后跑赢基准的比例，按评级分层看。
- 可解释：每个名字都能回答"为什么选它、什么情况下错了"。

**命名**：Autopilot 这个名字和它做的事相反。它是智囊，不是自动驾驶。

**理想状态**：读基础层只经 `lenses/`；战绩只从实绩层取；评级有度量且事后可验；同一个名字在智囊、Copilot、页面三处的读数与战绩一致。

### 2.4 操作面 · Copilot

**是什么**：人和 LLM 的**研究工作台**。它有基础层的全部能力可以直接调用：任何 lens、任何引擎、任何回测、任何战绩，人开口就能算、能验、能写。智囊的报告是它的**输入之一**，不是它的主要内容——人在这里做的研究，大部分是智囊没跑过的。

**三种用法，都是它的本职**：
1. **追问智囊**：这个名字为什么被提出、判官分歧在哪、评级怎么来的、换个条件会怎样。
2. **自己研究**：智囊的 objective 之外的任何问题——某个标的的波动面、某个事件前后的历史、某个想法的回测——直接调基础层。
3. **写下来**：假设、回测、playbook 规则，经审批 token 写进实绩层。

**它是终点**：所有人要读、要聊的东西最终落这里。Workbench 是不知道问题时去逛的地方，Copilot 是知道问题后去问的地方，智囊页面是配置和审计的地方，不是读报告的地方。

**理想状态**：基础层有的每个面 Copilot 都能用；智囊产出的每样东西 Copilot 都能引用并解释；不重复实现基础层的任何原语；写操作全部经审批、可追溯。

### 2.5 三个姿态在 UI 里的样子

- 每个 seat 只带自己的页面，seat 跟着路由走。
- 首页就是标题，没有不能点的分区文字（Portfolio 标准）。
- Overview 是无座页，讲三个姿态本身；蓝图与校准从它进入。

## 3. 理想的宽与深，以及它们怎么衔接

这一节定义**终态**。今天离它多远、先补哪边，在校准文档里，不在这里。

### 3.1 宽：理想的宇宙

**宽度是基础层的属性**，指有多少标的拥有**完整的**分析面。目标是：凡是股票面覆盖的标的，期权与波动面同样覆盖；不存在"半个标的"。宇宙的边界由一个明确的规则定义（可交易、有期权链、流动性阈值），而不是由哪张表碰巧有数据决定。

宽度的数据来自 Plugin 的采集（Research 按 D13 只读 `raw_market.*`），所以宽度的**需求**由 Research 定义，**供给**由 Plugin 与数据订阅决定。蓝图只定义需求。

### 3.2 深：理想的每标的覆盖

**深度是每个标的能被问多少个问题**。理想的深度对每个标的都一样：

- 趋势与结构（SEPA 四阶段、动量、路径）
- 波动面（IV rank / percentile、VRP、skew、期限结构、OpEx pin）
- 持仓面（GEX、dealer levels、资金流、order sentiment）
- 事件面（财报、宏观、日历）
- 预测面（terrain、forecast path、regime）
- 验证面（信号衰减命中、回测、结清战绩）

每一面在 registry 里有一个 lens，每个 lens 对覆盖的每个标的都会真的触发并回填命中。深度不分"重点标的"和"其他标的"：一个标的要么在宇宙里、拥有全部面，要么不在。

### 3.3 衔接：宽和深怎么合在一起用

**宽与深不是两个产品，是一个漏斗的两端**：

```
  宽（便宜、全宇宙）              深（贵、只对幸存者）
  ──────────────────►  筛  ────►  ──────────────────►  判
  趋势 / 动量 / 事件              波动面 / 持仓面 / 预测面 / 验证面
```

- **筛在宽处**：用便宜的面（趋势、动量、事件）在整个宇宙上筛，得到少量幸存者。
- **判在深处**：对幸存者用全部面做分析、回测、判官、评级。
- **契约在接缝**：任何一个通过筛选进入"判"的标的，**必须**拥有全部深面。筛选层不允许把一个没有深面的标的送到判断层；判断层不允许对缺面的标的静默出结论，要么拒绝、要么明说"这一面未测"。

这条接缝契约就是宽与深的交互方式。它让漏斗的每一层都可以独立做宽、做深，而不会出现"筛出四十三个，判的时候只剩五个有数据"这种事。

### 3.4 宽与深对四层各自意味着什么

| 层 | 宽 | 深 |
|---|---|---|
| 基础层 | 宇宙规则；每个面覆盖全宇宙 | 每个 lens 都真的触发 |
| 实绩层 | 每个标的的结清、命中都在 | 每个问题一个定义 |
| 智囊 | 筛选层跑全宇宙 | 判断层拿到全部面；缺面就说 |
| Copilot | 能问宇宙里任何标的 | 能问任何一面 |

## 4. 契约

契约是蓝图的可核对形式。编号稳定；**状态不在这里**，在校准文档里按编号记。

### 基础层

| 编号 | 契约 |
|---|---|
| C-F1 | 任何分析原语全系统只有一份实现 |
| C-F2 | 基础层不知道 objective、不知道谁在问 |
| C-F3 | 每个 lens 有 registry 条目、band、说明、页面路由 |
| C-F4 | 每个 lens 对它覆盖的每个标的都真的会触发 |
| C-F5 | 宇宙由明确规则定义，宇宙内每个标的拥有全部分析面（§3.1、§3.2） |

### 实绩层

| 编号 | 契约 |
|---|---|
| C-R1 | 每个"后来怎么样了"的问题有且只有一个定义与实现 |
| C-R2 | 提出的每个候选都会被结清 |
| C-R3 | Owner 的拒绝被记住，回来时说出变化 |
| C-R4 | lens 触发的命中会被回填 |
| C-R5 | 提案、审批、花费各有一条账 |
| C-R6 | 智囊的评级与 Copilot 的回答引用同一份战绩 |

### 智囊

| 编号 | 契约 |
|---|---|
| C-A1 | 读基础层只经 `lenses/`，不含直接读 `features.*` 的 SQL |
| C-A2 | 筛选是多层的，进入判断的标的拥有全部深面；缺面明说（§3.3） |
| C-A3 | 产出是带评级的报告，评级有度量且事后可验（§2.3 度量三条） |
| C-A4 | 报告回流 Copilot，可被追问 |
| C-A5 | 不执行、不下单、不扩容 |
| C-A6 | 名字说的就是它做的事 |
| C-A7 | 评级是智囊的产物：conviction、action、timing、levels、outlook、instrument、why、wrong_if 齐全，来源可追溯到基础层与实绩层 |
| C-A8 | 基础一端与高级一端都可用，同一层、同一套评级 |

### 操作面

| 编号 | 契约 |
|---|---|
| C-C1 | 所有人要读要聊的东西以它为终点 |
| C-C2 | 能用到基础层的全部面 |
| C-C3 | 不重复实现基础层 |
| C-C4 | 写操作经审批，账可追溯 |
| C-C5 | 可以在智囊的 objective 之外直接做研究：任何标的、任何面、任何回测，不需要先有一份报告 |

### UI

| 编号 | 契约 |
|---|---|
| C-U1 | 每个 seat 只带自己的页；seat 跟着路由走 |
| C-U2 | 同一个队列只数一次：徽章 = 页面 |
| C-U3 | 首页即标题，无不可点的分区 |
| C-U4 | 一个页面只亮一行（父子高亮除外） |

## 5. 不在范围内

- 交易执行的任何部分（D10 BLOCKED）。
- 写 Trade DB、写 `raw_market.*`（D13）。
- Plugin 的采集逻辑：Research 定义宽度的需求，不自己拉数据。
- Ops Console：平台不知道 SEPA 是什么，这是设计（双飞轮）。
